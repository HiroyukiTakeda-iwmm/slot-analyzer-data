## 5. 出典の記録（provenance）

### 5.1 置き場所

`provenance/<機種ID>.json` に置く（機種ID は `index.json` の id）。**機種ファイルには何も足さない。**

理由: アプリと pachi-manager はこのファイルを読まないので、公開中のアプリに影響しない。機種ファイルのスキーマ（`additionalProperties: false`）もアプリ側の検証も変えずに済む。

### 5.2 形

```json
{
  "machineId": "galfy",
  "machineFile": "galfy/galfy.json",
  "reviewedAt": "2026-09-26",
  "sources": [
    { "key": "chonborista", "kind": "analysis-site", "url": "https://chonborista.com/…", "retrievedAt": "2026-09-26" },
    { "key": "nana-press", "kind": "analysis-site", "url": "https://nana-press.com/…", "retrievedAt": "2026-09-26" }
  ],
  "items": [
    {
      "kind": "role",
      "name": "BIG",
      "status": "confirmed",
      "unit": "denominator",
      "values": { "chonborista": { "1": 295.2, "2": 292.6, "5": 284.9, "6": 277.7 }, "nana-press": { "1": 295.2, "2": 292.6, "5": 284.9, "6": 277.7 } },
      "adopted": { "1": 295.2, "2": 292.6, "5": 284.9, "6": 277.7 }
    }
  ],
  "candidates": [],
  "removed": [],
  "retiredIds": []
}
```

- `values` にはサイトごとの読み取り値を、表示の桁のまま入れる（確率は分母。書き方は 5.4）。サイトの本文や画像は入れない。出典に載っていない設定は書かない（キーを入れない）。分母の `null` は「確率 0」の意味で、「不明」には使わない。
- `adopted` は、選んだ出典の値そのもの（丸めの幅が重なる別の値にしない）。`kept-single-source` では、今の機種ファイルの値を unit の形にしたもの（確率なら `1 ÷ 確率`）そのもの。
- `reread` は `{ "by": 読み直した担当, "value": 読み直した値 }`。`provisional-chonborista` では必須。
- `candidates` は、見つけたが採用しなかった値（採用の基準を満たさない、サイト同士で食い違う）。
- `removed` は、その見直しで外した項目と根拠。形は `{ kind, name, unit, previous, values, appId, reason }`（`reread` は任意）。`previous` は外す前の機種ファイルの項目そのもの、`values` は調べた出典の値（見つからなければ `{}`）、`appId` は main でアプリがその項目に使っていた ID（ID を持つ項目だけに書き、ほかでは書かない）。例: `{ "kind": "role", "name": "中段チェリー", "unit": "denominator", "previous": { "name": "中段チェリー", "probabilities": { "1": 0.0001 }, "hasSettingDiff": false, "displayOrder": 7 }, "values": { "chonborista": { "1": 12000 } }, "appId": "chuudan_cherry_7", "reason": "今の値を裏づける出典なし" }`。後の PR で消してよい（前の値と理由は git の履歴に残る。採否ルールや出典を後で変えて通らなくなったら、消して直す）。書き換えはできない（書き換えた項目は、新しく外した項目として main と照らす）。
- `retiredIds` は、外した ID の台帳（5.8。2026-09-27）。1行は `{ kind, name, appId }`（すべて必須。ID を持つ項目だけ）。`removed` に `appId` を書いたら、同じ行をここに足す。**足すだけで、消さない・書き換えない**（外した項目を足し直しても残す）。

### 5.3 項目の状態（status）

| status | 意味 | 使える場面 |
|---|---|---|
| `confirmed` | 2サイト以上で一致、またはメーカー公式 | すべて |
| `provisional-chonborista` | ちょんぼりすたの値を、別の担当が読み直して一致した（確定値も食い違いも無く、ほかの出典がその値と矛盾しないとき。5.5） | 新しく入れる値。既存の見直しでは 5.5 の規則3 |
| `kept-single-source` | 既存の値で、1サイトだけが同じ値を出している | 既存の値 |

### 5.4 対象の項目と一致の判定

| 項目の種類 | 比べるもの | 一致の条件 |
|---|---|---|
| 小役・ボーナス・ゾーン内の役（確率） | 設定ごとの分母（確率 0 の設定は null） | すべての設定で丸めの幅が重なる（確率に直して比べる） |
| 試行成功率など（割合。役を除く数値の項目で、値の大きさは問わない） | 設定ごとの % | すべての設定で丸めの幅が重なる（確率に直して比べる） |
| 確定演出・終了画面・示唆（設定の組） | 確定する設定と否定する設定 | 組が完全に同じ |
| 設定と対応しない説明だけの項目 | 項目の有無 | 2つの出典にある（数値の比較はしない） |

サイトによって分母の丸め方が違う（1/295.2 と 1/295.24 など）ので、表示の桁で説明できる違いだけを同じ値とみなす（2026-09-27 に本人が決定。それまでの許容差は、丸めで説明できない違いを一致とし（295.2 と 295.4）、小数6桁で保存した小さい確率を一致としなかった（0.000076 と 1/13107.2）のでやめた）。

- 出典の値は、表示の桁のまま書く。数（`295.2`）か、表示の桁を残す文字列（`"300.0"`）。% で表示されている値は `"3.1%"` と書く（項目の unit が分母でも書ける）。分母の `null` と割合の `0` は「確率 0」
- それぞれの値は、表示の最後の桁の半分だけ幅を持つ（`295.2` → 分母 295.15〜295.25、`"3.1%"` → 3.05〜3.15%）。幅は確率に直して比べる
- 機種ファイルの確率は、小数6桁より粗くないとみなす（`0.000076` → 0.0000755〜0.0000765。末尾の 0 は JSON で消えるので、表示の桁数では決めない）
- 2つの値は、すべての設定で幅が重なれば一致。確率 0 は確率 0 とだけ一致
- 「残す」の判断、`kept-single-source` の採用値（`adopted`）と機種ファイルの値、main の値との比較は、機種ファイルの確率の幅（`storedInterval`）で比べる。分母に直した値（`1 ÷ 確率`）の桁では比べない。確定・暫定の値は、採用値を有効数字6桁にした値そのものを機種ファイルに書くので、幅では比べない（5.6）

一部の設定だけを載せる出典（数値の項目。2026-09-27）: 値の設定（キー）が、その項目が持つべき設定（新しい値は機種の設定、既存の値と記録の確かめは機種ファイルの確率のキー。どちらも機種のすべての設定）とちょうど同じものを「そろっている」、そうでないものを「一部だけ」という。

- 合う: そろった値どうしで、すべての設定の幅が重なる（上の「一致」）
- 矛盾しない: 値 p の設定がすべて値 v にあり（1つ以上）、その設定ごとに幅が重なる
- 互いに矛盾しない: 2つの値に共通の設定が1つ以上あり、共通の設定ごとに幅が重なる

採用の候補は、そろっている値だけ（5.5）。一部だけの出典は、採用値と矛盾しなければ数えない。

採用する値は、メーカー公式 → ちょんぼりすた → 最初に見つかった出典の順で選ぶ。

比べるもの（記録の unit）の候補は、項目の種類と機種ファイルの値で決まる。役は分母。ほかの数値の項目は、値の大きさによらず分母か割合（2026-09-27 に本人が決定。それまでの「0 でない値がすべて 10% 以上なら」の下限はやめた。表示の桁が粗い出典の丸めの幅が広い（3.1% と書くと 3.05〜3.15%）のは、その出典の精度そのもので、比べ方の誤りではない。% の表示は下限があったときも分母の値に "3.1%" と書けたので、下限をやめた効果は、小さい割合でも割合を名乗れることと、割合の数（3.14）で書けること）。数値が無く確定・否定の設定の欄があれば（中身が空の配列でも）設定の組、どちらも無ければ有無。候補を項目で決めるのは、記録する側が自由に選べると、緩い比べ方にして値の照合を外せてしまうため。候補が分母と割合の2つのときは、出典の表示の形に合わせて選ぶ（換算しない。validate はこれを確かめられない）。確率 0 の設定は、分母では null と書く。数値と設定の組の両方がある項目（2026-09-26 時点で6件）は数値の側で照合し、設定の組の側の扱いは段階2で決める。最上位の終了画面の `distribution` も確率として扱う（アプリの移行処理が `probabilities` に改名して使う古い形。グループの中の終了画面は改名しないので扱わない）。

`patterns` 形式（2026-09-27 に本人が決定）: 最上位の終了画面の `patterns` は記録できない（アプリは終了画面の patterns を別々の終了画面に展開する）。見直す機種では、先に `scripts/expand-patterns.mjs` で、アプリが読む形（パターンごとの普通の終了画面）に書き直してから記録する。書き直した終了画面は、アプリの移行処理が作る値（id・name・type・hint・confirmedSettings と、親にあれば color）をそのまま持ち、id は明示の id として書く（アプリが作る ID は変わらない）。書き直した機種を移行処理に通した結果が元と同じことを、道具が確かめ（違えば書き直さない）、テストが実データ（2026-09-27 時点で17機種）で確かめる。アプリが読む形が同じなので、書き直しだけでは機種の版を上げない。`patterns` 形式は新しく使わない。ボイスの `patterns` はアプリが読み込み時に捨てるので書き直さず、扱いは段階2で決める（それまで記録できない）。グループの中の終了画面の `patterns` も書き直さない（アプリも展開しない。2026-09-27 時点で0件）。

項目は「種類＋名前」で見分ける。同じ種類で同じ名前の項目が複数あるときは、並び順で2つ目から名前に `#2`、`#3` を付けて区別する（2026-09-26 時点で tekken5 に9組、valvrave2 に2組。どれもデータに明示の `id` がある別の終了画面）。

### 5.5 採否のルール

確定値の決め方（数値の項目。言葉は 5.4。2026-09-27 に決定）:

1. 採用の候補は、そろっている値だけ。一部だけの値は採用値にならない（アプリは設定が1つでも欠けた確率があると推定全体を止めるため）
2. そろっている公式があれば、公式の中で記録順の最初を採用値にする。ほかの公式（そろっている・一部だけ）が1つでもその値と矛盾すれば食い違い。公式以外の出典は見ない（公式が優先）
3. そろっている公式が無ければ、そろっている出典を優先順（ちょんぼりすた → 記録順）に見て、その値と合うそろっている出典が自分を含めて2つ以上ある最初の値を採用値にする（一部だけの出典は数えない）
4. 3 で採用値が決まったら、食い違いを確かめる。採用値と矛盾する出典（そろっている・一部だけ）のうち、互いに矛盾しない2つがあれば食い違い（別の値の組）。一部だけの公式が採用値と矛盾するときも食い違い（公式が優先）

幅の重なりは推移しない（A と B、B と C が重なっても、A と C は重ならないことがある）。そのため、採用値は優先順（公式 → ちょんぼりすた → 記録順）の最初に条件を満たす値で決まり、記録順が同じなら結果も1つに決まる（例: 設定1だけの項目で 295.2・295.25・295.26・295.265 の順に記録すると、295.2 を採って、それと矛盾して互いに合う 295.26・295.265 があるので食い違い。295.25 を先に記録すると、矛盾するのは 295.265 だけなので 295.25 で確定）。

一部だけの出典は `values` に記録し、採用値と矛盾しなければ数えない（確定にも食い違いにも使わない）。設定の組・有無の項目は今までどおり、公式の値か、別の値で一致する組の無い2サイト以上の完全な一致。

ちょんぼりすたの暫定（`provisional-chonborista`）の条件（新しい値・既存の値で同じ。数値の項目。2026-09-27）: 確定値も食い違いも無く、ちょんぼりすたの値がそろっていて、ほかのどの出典もその値と矛盾せず、別の担当の読み直しがちょんぼりすたの値と合う（矛盾しない一部だけの出典があっても暫定にできる）。設定の組・有無の項目は今までどおり、ちょんぼりすたにしか無いこと。

新しく入れる値（新台の項目、既存機種に新しく足す項目）:

1. 確定値がある（公式、または2サイト以上で一致）→ 入れる（`confirmed`）
2. ちょんぼりすたの暫定の条件を満たす → 暫定で入れる（`provisional-chonborista`）
3. それ以外（ちょんぼりすた以外の1サイトだけ、サイト同士で食い違う、そろった出典が無い）→ 入れない（`candidates` に記録）

`candidates` の理由は、次の上から最初に当たったものにする（2026-09-27）: 出典なし／全設定の値がそろった出典が無い（アプリは設定が1つでも欠けた確率があると推定が止まる）／サイト間で食い違い（確定値を探して食い違った）／ちょんぼりすたの値と矛盾する出典がある／ちょんぼりすたの値だけで、読み直しが無いか一致しない／全設定がそろった出典が1つだけ（ちょんぼりすた以外）／サイト間で食い違い（全設定がそろった出典が2つ以上あるが、合う組が無い）。設定の組・有無の項目の値は設定ごとではないので、どれも「そろっている」とみなし、「全設定の値がそろった出典が無い」は使わず、「全設定がそろった出典が1つだけ」の代わりに段階0の文面「ちょんぼりすた以外の1サイトのみ」にする。

採用の候補がそろった値だけなので、入れる値は機種のすべての設定の値を持つ（2026-09-27 に本人が決定）。

既存の値（見直し）:

1. 確定値 V がある → V にする（`confirmed`。今の値と違えば訂正）
2. 今の値と同じ値を出しているサイトが1つだけある → 残す（`kept-single-source`。機種ファイルの値は変えない）
   - 一部の設定だけを載せる出典も、載っている設定がすべて機種ファイルの確率と合えば（5.4 の幅）、裏づけに数える（2026-09-27 に本人が決定）
3. 今の値はどのサイトとも合わないが、ちょんぼりすたの暫定の条件を満たす → その値にする（`provisional-chonborista`）
4. それ以外 → 外す（`removed` に前の値と理由を残し、ID を持つ項目なら `appId` と同じ行を `retiredIds` に足す）

3 は、本人の2つの回答（既存の値は「1件なら残す・0件なら外す」、ちょんぼりすたにしか無い値は「暫定として入れる」）を組み合わせた解釈である。今の値を裏づける出典が0件で、ちょんぼりすたが別の値を出している（ほかの出典はその値と矛盾しない）場合に、外すのではなく、ちょんぼりすたの値を暫定として採用する。

### 5.6 数値の保存

確率は `1/分母` を**有効数字6桁**で保存する。今の多くは「小数6桁」なので、1/65536 のような小さい確率では約1.7%ずれる。見直しで書き換える機種からこの形にそろえる。

確定・暫定（`confirmed`・`provisional-chonborista`）の値は、採用値を有効数字6桁にした値（`toStoredFromShown`）を書く（validate が、機種ファイルの確率がすべての設定でその値そのものかを確かめる。小数6桁の幅は小さい確率ほど広く、1/65536 を 0.000015 と書いた約1.7%のずれも幅に入るので、幅では比べない）。残す値（`kept-single-source`）は変えない（2026-09-27 に決定）。

### 5.7 検証（`npm run validate` に足す）

- provenance ファイルのスキーマ検証
- 機種ファイルとの整合（provenance がある機種だけ）
  - 機種ファイルの各項目（5.4 の種類）が `items` にあり、status が 5.3 のどれかである
  - 機種ファイルの値と `adopted` が合う（unit は項目の種類と中身で決まるものを使う）。`confirmed`・`provisional-chonborista` の数値は、機種ファイルの確率が採用値を有効数字6桁にした値そのもの（5.6）。`kept-single-source` の数値と、設定の組・有無は、5.4 の条件で一致する
  - `candidates` と `removed` の項目が機種ファイルに無い
  - `removed`（2026-09-27）: `values` の出典キーが `sources` にあり、`unit` が `previous` の種類と中身で決まるもの（最上位の終了画面の `distribution` は `probabilities` として読む。items と同じ文面）、値と `reread` の形が unit に合う。`previous` を今の値として、既存の値の採否ルールが「外す」を選ぶ（5.5 の規則4。選ばなければ `外す条件に合わない（<status> にできる）`）。読み直しが無く、ちょんぼりすたの値と合う読み直しがあれば暫定（規則3）になる場合は、外す前に読み直しを求める（読み直しを省いて規則3を素通りさせない）。`appId` は ID を持つ項目（5.8）だけに書き、ほかでは書かない。`appId` を書いたら、同じ `kind`・`name`・`appId` の行が `retiredIds` にある
  - `retiredIds`（外した ID の台帳。2026-09-27）: ID を持つ種類の行だけで、同じ行が2つ無い。今の機種ファイルの ID を持つ項目が、台帳の `appId` を同じ範囲（ゾーン内の役とグループ内の終了画面は親ごと）で使っていれば止める（`<項目>: 外した項目の ID（<ID>）を使っている（既存の項目なら main の ID を id に書いて固定する。新しい項目なら別の明示の id を付ける）`）。main を読まずに止めるので、PR をまたいでも、外した項目を足し直した後でも効く。名前から作る ID が繰り上がって重なった既存の項目は main の ID で固定する（別の新しい id にすると check:base が「ID が変わった」で止める）
  - `sources` のどれにも `url` と `retrievedAt` があり、URL のサイト（登録ドメイン。サブドメインは同じサイトに数える）が重ならない（同じサイトを2つの出典として数えない。URL として読めない出典は、サイトが分からないのでエラーにする）。`official`（メーカー公式）の出典は、URL のサイトがメーカーの公式ドメインの一覧（`config/official-domains.json`）にあること（2026-09-27。無ければ `公式の出典のドメインが一覧（config/official-domains.json）に無い: <サイト>`）
  - 公式ドメインの一覧（2026-09-27）: `{ "domains": [{ "domain", "maker", "evidence", "checkedAt" }] }` を `schemas/official-domains.schema.json` で確かめる。`domain` は登録ドメインそのもの（出典のサイトと同じ計算で、`www.`・サブドメイン・大文字を付けない）で重複しない、`evidence` はそのドメインがメーカーのものだと確かめた会社情報のページ（https の URL）、`checkedAt` は確かめた日。最初は空で入れ、段階1b で公式の出典を初めて使う PR で足す。一覧が無い・読めない・スキーマや決まりに合わないときは、空の一覧として続けずに一覧のエラーにし、公式の出典も「確かめられない」エラーにする（黙って通さない・黙って落とさない）
  - status と値の関係が 5.5 の採否ルールと合う（採否ルールと同じ判断で確定値を求め直して比べる）
- main と比べて確かめること（`npm run check:base`。validate は main を読まないので、こちらで見る）
  - `kept-single-source` は main にある項目にだけ使い、採用値と機種ファイルの値が main の値そのもの（「残す」は値を変えないこと。丸めの幅の重なりによる一致は推移しないので、完全一致で結ぶ）
  - main にある項目の `provisional-chonborista` は、main の値を裏づける出典（ちょんぼりすた以外・一部だけの出典も含む）が無いときだけ（あれば、既存の値の順「確定 → 残す → 暫定 → 外す」で 5.5 の規則2の `kept-single-source` が先に当たる。数え方は「残す」の判断と同じで、数値は main の確率の幅と、出典の値に載っている設定だけを比べる）
  - 上の2つ（`kept-single-source`・`provisional-chonborista` の確かめ）は、記録か機種ファイルの値が main から変わった項目と、新しい項目だけに行う（2026-09-29）。main の出典記録（main の `provenance/` を列挙して読む）の同じ機種に、JSON として同じ項目（`kind`・`name`・`unit`・`status`・`adopted`・`values`・`reread`。キーの順は問わない）があり、機種ファイルの値（unit の形の値）も main と同じ項目は、main に入れたときに確かめを通った採用として、確かめ直さない。確かめ直すと、暫定の値を入れた後の main ではちょんぼりすたの値が main の値を裏づけるので、関係ない PR が止まる。どちらかの機種ファイルに項目が無いか、値を unit の形にできなければ確かめる
  - main の機種の項目は、最上位の終了画面の `patterns` をアプリが読む形（パターンごとの普通の終了画面。`expand-patterns` と同じ計算）に書き直してから比べる（2026-09-29。上の採否ルールの確かめと、下の `removed` の確かめ）。同じ PR で `patterns` を書き直して、書き直した終了画面を外す・残すため。`patterns` の親は main の項目に無い（アプリは親を読まない）。main が書き直せない形なら比べられない（終了コード 2）
  - ID を持つ項目（5.8）の ID が変わっていない。main で明示の `id` があった確定演出などが、`id` を失う・別の `id` になるのも止める
  - ID を持たない項目（明示の `id` の無い確定演出・試行成功率・ボイス・楽曲・演出・モード移行と、特殊設定）も、消したら `removed` に記録されている（5.5 の既存の値の規則4。ID を持つ項目は上の ID の検査が同じ文面で報告する）
  - 新しく足した機種（main の index.json に無い機種）に、出典記録がある（新しく入れる値は 5.5 の採否ルールを通す）
  - ID を作る種類で同じ名前の項目に、別々の明示の `id` がある（5.8）
  - 新しく足した確定演出・試行成功率・ボイス・楽曲・演出・モード移行（main に無い項目キー。新しい機種の項目も）に、明示の `id` がある（5.8。2026-09-27）
  - `removed` と外した ID の台帳（5.8。2026-09-27）: 新しく外した項目（main の同じ機種の記録に JSON として同じ項目が無いもの）は、main の機種ファイルにあり、`previous` が main の機種ファイルの項目と JSON として同じ（キーの順は問わない。外す条件の確かめを作った値で通せないように。最上位の終了画面の `distribution` は改名しない。`patterns` を書き直した終了画面は、書き直した後の形（アプリが読む形）と比べる）。`appId` は、main にその項目の ID があれば main の ID と同じ。main の記録の `removed` は消してよいが、`retiredIds` の各行は比べる側の同じ機種の記録に残す（消さない・書き換えない。例外なし。main の記録は main の `provenance/` を列挙して読むので、記録のファイルごと消しても見つかる。行を書き換えると、元の行を消したものとして1件報告する）。台帳の ID の再利用は validate が止め、main にある ID の使い回しは上の ID の検査が報告する（同じ誤りを2回報告しない）
- 段階3で「全機種に provenance が必須」を有効にする。それまでは、記録がまだ無い機種の値を直す PR に記録は求めない（記録がある機種では、記録も直す。記録を置く機種では、すべての項目を `items` に書く）

### 5.8 アプリの ID を変えない

アプリは、役・ゾーン・終了画面・終了画面グループの ID を名前から作る（2026-09-26 にコードで確認）。

| 項目 | ID の作り方 |
|---|---|
| 役（ゾーン内の役も） | 名前のローマ字 + `_` + displayOrder（名前が漢字だけなら `role_` + displayOrder） |
| 終了画面・ゾーン・終了画面グループ | 名前のローマ字（漢字だけなら `endscreen` など） |
| 共通 | データに `id` があればそれを使う。同じ ID が重なると、並び順に `_2`、`_3` を付ける |
| 確定演出・試行成功率・ボイス・楽曲・演出・モード移行 | データの `id` をそのまま使う。無ければ、取り込むたびに乱数の ID を振る（`x.id \|\| generateUUID()`。重なっても `_2` を付けない） |

**ID を持つ項目**は、役・ゾーン内の役・終了画面・グループ内の終了画面（名前から作る ID。ゾーン・終了画面グループも）と、明示の `id` がある確定演出・試行成功率・ボイス・楽曲・演出・モード移行（`id` そのもの）。ID が重なってはいけない範囲は、種類ごと（ゾーン内の役とグループ内の終了画面は親ごと）。2026-09-27 に、アプリのコード（slot-analyzer-ios の `services/githubMachineService.ts`）で、確定演出などの `id` もセッションの記録（確定演出の出現・試行の成否・ボイスの数など）を結ぶことを確かめた。記録の ID が機種データに無いと、推定は「記録に対応する機種データがありません」になる。

利用者の記録はこの ID でつながっているので、ID を持つ項目について次を守る。

- 既存の項目の `name` と `displayOrder` を変えない。並べ替えもしない
- 新しい項目は、今ある項目の後ろに足す（役の displayOrder は今の最大値＋1）
- 項目を外すときは、provenance の `removed` に記録し、ID を持つ項目なら `retiredIds` に足す
- 外したり足したりして、ほかの項目の `_2` などが繰り上がる場合は、残す項目に今の ID を `id` として書いて固定する（名前が漢字だけの終了画面などで起きる）
- 外した項目の ID を、新しい項目に使わない（利用者の記録が別の項目に付くため）。名前から作る ID が外した項目と重なるとき（漢字だけの名前など）は、新しい項目に明示の `id` を付ける
- ID を作る種類で同じ名前の項目には、別々の明示の `id` を付ける（1つ目を外したとき、2つ目が1つ目の ID を黙って引き継ぐため。明示の `id` が重なっていても、並び順で `_2` が付くので同じことが起きる）
- 確定演出・試行成功率・ボイス・楽曲・演出・モード移行の明示の `id` を、変えない・消さない。新しく足す項目には明示の `id` を付ける（無いと、取り込むたびに乱数の ID になり、数えた記録が切れる。`npm run check:base` が止める）。同じ機種の同じ種類で `id` を重ねない（アプリは `_2` を付けないので記録が混ざる。`npm run validate` が止める）。今ある `id` の無い項目（2026-09-27 時点でボイス2件・モード移行1件）は、段階1a では変えない
- `npm run check:base` で、main と比べて既存の ID が変わっていないか、記録なしに消えた項目がないか、新しい項目が main の別の項目の ID を使っていないかを確かめる。PR の CI でも実行する
- 外した項目の ID は、出典記録の `retiredIds`（外した ID の台帳。2026-09-27）に `{ kind, name, appId }` で足し、消さない（`npm run check:base` が、main の記録の行が残っているかを確かめる）。今の機種ファイルの項目がその ID を同じ範囲で使えば `npm run validate` が止めるので、先の PR で外した項目の ID を後の PR の新しい項目が使っても止まる（main の機種ファイルにはもう無い ID でも見つかる）。外した項目を足し直すときは、`removed` から消し（validate の「外したはずの項目が機種ファイルにある」があるため）、明示の別の `id` を付ける（`retiredIds` は残すので、前の ID は使えない）

特殊設定は ID を持たない。確定演出などで明示の `id` の無い項目は、アプリが取り込むたびに乱数の ID を振るので、ID を変えない・再利用しないの対象外（消したら `removed` には書く）。

## 6. 調べ方

### 6.1 出典の優先順

1. **ちょんぼりすた**（最初に読む）
2. メーカー公式（公表値があれば、採用する値として最優先）
3. なな徹・一撃・DMMぱちタウン・スロパチクエスト（2つ目の確認）
4. P-WORLD（導入日と機種の基本情報の確認）

### 6.2 1機種の流れ

1. ちょんぼりすたの機種ページを探し、5.4 の項目を抜き出す（作業メモは git 対象外の `slot-analyzer-data-temp/` に置く）
2. 2つ目の出典で、同じ項目を抜き出す
3. 照合スクリプトで status を決める
4. 機種ファイル、provenance ファイル、`index.json` の該当行を作る・直す
   - 値を変えたら機種の `version` を上げ、`index.json` の同じ機種の `version` と一致させる
   - `lastUpdated` を更新する。`source` にはサイト名と URL を並べる
   - 説明文は自分の言葉で書き、`index.json` の説明と食い違わないようにする
5. 抜き出しをしていない別の担当が、出典ページを読み直して値を照合する。読み直す担当には機種名・出典 URL・項目名だけを渡し、採用した値は見せない（先に答えを見ると、それに合わせて読んでしまうため）。照合はスクリプトで行う。`provisional-chonborista` の値は必ずこの読み直しを通す

### 6.3 取得のしかた

- ページをそのまま取得して読む（ちょんぼりすた・なな徹は、2026-09-26 にどちらも HTTP 200 で読めた）。弾かれたら Chrome に切り替える。それでも読めなければ「未確認」とし、別の値で埋めない
- 同じサイトへのアクセスは数秒あける
- 取り込むのは数値、項目名、設定との対応だけ

### 6.4 新台の洗い出し

導入日の一覧を2系統（ちょんぼりすたの新台一覧と P-WORLD など）で突き合わせ、2026-06-01〜2026-09-25 に導入されたパチスロを並べる。パチンコ、登録済みの機種、実在しない機種は除く。結果は `machines/FUTURE_ADDITIONS.md` に反映する。
