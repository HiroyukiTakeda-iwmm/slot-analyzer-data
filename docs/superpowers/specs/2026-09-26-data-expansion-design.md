## 5. 出典の記録（provenance）

### 5.1 置き場所

`provenance/<機種ID>.json` に置く（機種ID は `index.json` の id）。**機種ファイルには何も足さない。**

理由: アプリと pachi-manager はこのファイルを読まないので、公開中のアプリに影響しない。機種ファイルのスキーマ（`additionalProperties: false`）もアプリ側の検証も変えずに済む。

### 5.2 形

```json
{
  "machineId": "galfy",
  "machineFile": "galfy/galfy.json",
  "reviewedAt": "2026-09-26",
  "sources": [
    { "key": "chonborista", "kind": "analysis-site", "url": "https://chonborista.com/…", "retrievedAt": "2026-09-26" },
    { "key": "nana-press", "kind": "analysis-site", "url": "https://nana-press.com/…", "retrievedAt": "2026-09-26" }
  ],
  "items": [
    {
      "kind": "role",
      "name": "BIG",
      "status": "confirmed",
      "unit": "denominator",
      "values": { "chonborista": { "1": 295.2, "2": 292.6, "5": 284.9, "6": 277.7 }, "nana-press": { "1": 295.2, "2": 292.6, "5": 284.9, "6": 277.7 } },
      "adopted": { "1": 295.2, "2": 292.6, "5": 284.9, "6": 277.7 }
    }
  ],
  "candidates": [],
  "removed": []
}
```

- `values` にはサイトごとの読み取り値を入れる（確率は分母）。サイトの本文や画像は入れない。出典に載っていない設定は書かない（キーを入れない）。分母の `null` は「確率 0」の意味で、「不明」には使わない。
- `adopted` は、選んだ出典の値そのもの（許容差の中の別の値にしない）。`kept-single-source` では、今の機種ファイルの値を unit の形にしたもの（確率なら `1 ÷ 確率`）そのもの。
- `reread` は `{ "by": 読み直した担当, "value": 読み直した値 }`。`provisional-chonborista` では必須。
- `candidates` は、見つけたが採用しなかった値（採用の基準を満たさない、サイト同士で食い違う）。
- `removed` は、見直しで外した値。前の値と理由を残す。

### 5.3 項目の状態（status）

| status | 意味 | 使える場面 |
|---|---|---|
| `confirmed` | 2サイト以上で一致、またはメーカー公式 | すべて |
| `provisional-chonborista` | ちょんぼりすたにしか無く、別の担当が読み直して一致した | 新しく入れる値。既存の見直しでは 5.5 の規則3 |
| `kept-single-source` | 既存の値で、1サイトだけが同じ値を出している | 既存の値 |

### 5.4 対象の項目と一致の判定

| 項目の種類 | 比べるもの | 一致の条件 |
|---|---|---|
| 小役・ボーナス・ゾーン内の役（確率） | 設定ごとの分母（確率 0 の設定は null） | すべての設定で差が 0.1% 以内（\|a−b\| ÷ 大きい方） |
| 試行成功率など（割合。0 でない値がすべて 10% 以上のもの） | 設定ごとの % | すべての設定で差が 0.1 ポイント以内 |
| 確定演出・終了画面・示唆（設定の組） | 確定する設定と否定する設定 | 組が完全に同じ |
| 設定と対応しない説明だけの項目 | 項目の有無 | 2つの出典にある（数値の比較はしない） |

0.1% まで許すのは、サイトによって分母の丸め方が違うため（1/295.2 と 1/295.24 など）。採用する値は、メーカー公式 → ちょんぼりすた → 最初に見つかった出典の順で選ぶ。

比べるもの（記録の unit）は、項目の種類と機種ファイルの値で決まる。役は分母。ほかの数値の項目は、0 でない値がすべて 10% 以上なら分母か割合、それ以外は分母（割合の 0.1 ポイントの許容差は、小さい値には緩すぎる。試行成功率の項目には BB 確率のような小さい確率も入っている）。数値が無く確定・否定の設定の欄があれば（中身が空の配列でも）設定の組、どちらも無ければ有無。記録する側が選べると、緩い比べ方にして値の照合を外せてしまうため。確率 0 の設定は、分母では null と書く。数値と設定の組の両方がある項目（2026-09-26 時点で6件）は数値の側で照合し、設定の組の側の扱いは段階2で決める。`distribution` も確率として扱う（アプリの移行処理が `probabilities` に改名して使う終了画面の古い形）。`patterns` 形式は段階1で形を決めるまで記録できない（アプリは終了画面の patterns を別々の終了画面に展開する）。

項目は「種類＋名前」で見分ける。同じ種類で同じ名前の項目が複数あるときは、並び順で2つ目から名前に `#2`、`#3` を付けて区別する（2026-09-26 時点で tekken5 に9組、valvrave2 に2組。どれもデータに明示の `id` がある別の終了画面）。

### 5.5 採否のルール

新しく入れる値（新台の項目、既存機種に新しく足す項目）:

1. 2サイト以上で一致、またはメーカー公式にある → 入れる（`confirmed`）
2. ちょんぼりすたにしか無く、別の担当が読み直して一致した → 暫定で入れる（`provisional-chonborista`）
3. それ以外（ちょんぼりすた以外の1サイトだけ、サイト同士で食い違う）→ 入れない（`candidates` に記録）

既存の値（見直し）:

1. 2サイト以上で一致した値 V がある → V にする（`confirmed`。今の値と違えば訂正）
2. 今の値と同じ値を出しているサイトが1つだけある → 残す（`kept-single-source`。機種ファイルの値は変えない）
3. 今の値はどのサイトとも合わないが、ちょんぼりすたにだけ値があり、読み直しで一致した → その値にする（`provisional-chonborista`）
4. それ以外 → 外す（`removed` に前の値と理由を残す）

3 は、本人の2つの回答（既存の値は「1件なら残す・0件なら外す」、ちょんぼりすたにしか無い値は「暫定として入れる」）を組み合わせた解釈である。今の値を裏づける出典が0件で、ちょんぼりすただけが別の値を出している場合に、外すのではなく、ちょんぼりすたの値を暫定として採用する。

### 5.6 数値の保存

確率は `1/分母` を**有効数字6桁**で保存する。今の多くは「小数6桁」なので、1/65536 のような小さい確率では約1.7%ずれる。見直しで書き換える機種からこの形にそろえる。

### 5.7 検証（`npm run validate` に足す）

- provenance ファイルのスキーマ検証
- 機種ファイルとの整合（provenance がある機種だけ）
  - 機種ファイルの各項目（5.4 の種類）が `items` にあり、status が 5.3 のどれかである
  - 機種ファイルの値と `adopted` が、5.4 の条件で一致する（unit は項目の種類と中身で決まるものを使う）
  - `candidates` と `removed` の項目が機種ファイルに無い
  - `sources` のどれにも `url` と `retrievedAt` があり、URL のサイト（登録ドメイン。サブドメインは同じサイトに数える）が重ならない（同じサイトを2つの出典として数えない）。`official` は記録する側の申告で機械では確かめられないので、手順で確かめる
  - status と値の関係が 5.5 の採否ルールと合う（採否ルールと同じ判断で確定値を求め直して比べる）
- main と比べて確かめること（`npm run check:base`。validate は main を読まないので、こちらで見る）
  - `kept-single-source` は main にある項目にだけ使い、採用値と機種ファイルの値が main の値そのもの（「残す」は値を変えないこと。許容差による一致は推移しないので、完全一致で結ぶ）
  - main にある項目の `provisional-chonborista` は、ちょんぼりすたの値が main の値と一致しないときだけ（一致するなら 5.5 の規則2で `kept-single-source`）
  - アプリが作る ID が変わっていない（5.8）
  - ID を持たない種類の項目（確定演出・試行成功率・ボイス・楽曲・演出・モード移行・特殊設定）も、消したら `removed` に記録されている（5.5 の既存の値の規則4）
  - 新しく足した機種（main の index.json に無い機種）に、出典記録がある（新しく入れる値は 5.5 の採否ルールを通す）
  - ID を作る種類で同じ名前の項目に、明示の `id` がある（5.8）
- 段階3で「全機種に provenance が必須」を有効にする。それまでは、記録がまだ無い機種の値を直す PR に記録は求めない（記録がある機種では、記録も直す。記録を置く機種では、すべての項目を `items` に書く）

### 5.8 アプリが作る ID を変えない

アプリは、役・ゾーン・終了画面・終了画面グループの ID を名前から作る（2026-09-26 にコードで確認）。

| 項目 | ID の作り方 |
|---|---|
| 役（ゾーン内の役も） | 名前のローマ字 + `_` + displayOrder（名前が漢字だけなら `role_` + displayOrder） |
| 終了画面・ゾーン・終了画面グループ | 名前のローマ字（漢字だけなら `endscreen` など） |
| 共通 | データに `id` があればそれを使う。同じ ID が重なると、並び順に `_2`、`_3` を付ける |

利用者の記録はこの ID でつながっているので、次を守る。

- 既存の項目の `name` と `displayOrder` を変えない。並べ替えもしない
- 新しい項目は、今ある項目の後ろに足す（役の displayOrder は今の最大値＋1）
- 項目を外すときは、provenance の `removed` に記録する
- 外したり足したりして、ほかの項目の `_2` などが繰り上がる場合は、残す項目に今の ID を `id` として書いて固定する（名前が漢字だけの終了画面などで起きる）
- 外した項目の ID を、新しい項目に使わない（利用者の記録が別の項目に付くため）。名前から作る ID が外した項目と重なるとき（漢字だけの名前など）は、新しい項目に明示の `id` を付ける
- ID を作る種類で同じ名前の項目には、明示の `id` を付ける（1つ目を外したとき、2つ目が1つ目の ID を黙って引き継ぐため）
- `npm run check:base` で、main と比べて既存の ID が変わっていないか、記録なしに消えた項目がないか、新しい項目が main の別の項目の ID を使っていないかを確かめる。PR の CI でも実行する
- 先の PR で外した項目の ID を、後の PR の新しい項目が使う場合は、main と比べるだけでは分からない（main にはもう無いため）。段階2で項目を外す前に、外した ID を出典記録に残して確かめる仕組みを足す

確定演出・試行成功率・ボイス・楽曲・演出・モード移行は、データに `id` が無ければ、アプリが取り込むたびに乱数の ID を振る。このため、この制約の対象外とする。

## 6. 調べ方

### 6.1 出典の優先順

1. **ちょんぼりすた**（最初に読む）
2. メーカー公式（公表値があれば、採用する値として最優先）
3. なな徹・一撃・DMMぱちタウン・スロパチクエスト（2つ目の確認）
4. P-WORLD（導入日と機種の基本情報の確認）

### 6.2 1機種の流れ

1. ちょんぼりすたの機種ページを探し、5.4 の項目を抜き出す（作業メモは git 対象外の `slot-analyzer-data-temp/` に置く）
2. 2つ目の出典で、同じ項目を抜き出す
3. 照合スクリプトで status を決める
4. 機種ファイル、provenance ファイル、`index.json` の該当行を作る・直す
   - 値を変えたら機種の `version` を上げ、`index.json` の同じ機種の `version` と一致させる
   - `lastUpdated` を更新する。`source` にはサイト名と URL を並べる
   - 説明文は自分の言葉で書き、`index.json` の説明と食い違わないようにする
5. 抜き出しをしていない別の担当が、出典ページを読み直して値を照合する。読み直す担当には機種名・出典 URL・項目名だけを渡し、採用した値は見せない（先に答えを見ると、それに合わせて読んでしまうため）。照合はスクリプトで行う。`provisional-chonborista` の値は必ずこの読み直しを通す

### 6.3 取得のしかた

- ページをそのまま取得して読む（ちょんぼりすた・なな徹は、2026-09-26 にどちらも HTTP 200 で読めた）。弾かれたら Chrome に切り替える。それでも読めなければ「未確認」とし、別の値で埋めない
- 同じサイトへのアクセスは数秒あける
- 取り込むのは数値、項目名、設定との対応だけ

### 6.4 新台の洗い出し

導入日の一覧を2系統（ちょんぼりすたの新台一覧と P-WORLD など）で突き合わせ、2026-06-01〜2026-09-25 に導入されたパチスロを並べる。パチンコ、登録済みの機種、実在しない機種は除く。結果は `machines/FUTURE_ADDITIONS.md` に反映する。

## 9. アプリとの連携確認

### 9.1 自動（毎バッチ）

slot-analyzer-ios の作業ツリー（build 15 のソースと同じ）で次を実行する。

```bash
SLOT_DATA_ROOT=<worktree> npm run test:data-contract
```

本番の取得・検証・変換の処理をそのまま通すので、「データ側の検証は通るのに、アプリでは弾かれる」ずれを捕まえられる。基準値は 2026-09-26 に 150 件すべて合格（index 1 件と 149 機種）。

### 9.2 実機（iWphone-sub・iPhone ミラーリング）

- 準備（段階0）: TestFlight の build 15 をサブの iPhone に入れる。内部テストの配布設定を確かめる
- マージ前: PR ブランチの機種ファイルの raw URL を、アプリの「URL から追加」で読み込み、確率一覧と設定推測を確かめる。アプリの URL 取り込みは https の JSON を本番と同じスキーマで検証する（2026-09-26 にコードで確認）
  - 段階1: 追加する新台すべて
  - 段階2: 各バッチ2〜3機種と、値を外した機種すべて
- マージ後: アプリで同期して、件数と「更新」の表示を確かめる（段階1、段階2の最初と最後のバッチ、値を外したバッチ）
- 取り合いを防ぐ: 使う前に他のセッション（焼売など）へ声をかけ、終わったら知らせる。メインの iPhone は使わない
- 撮影するのはアプリの画面だけ

## 10. 版と記録

- `index.json` と `package.json` の version: 段階0は据え置き。データを変える PR ごとにマイナー版を上げる（3.9.0、3.10.0 …）
- 機種の version: 新台は 1.0 から。値を変えたら上げる
- 毎 PR で CHANGELOG・README（`npm run quality` の出力をそのまま転記）・`machines/FUTURE_ADDITIONS.md` を更新する
- マージのたびに作業台帳（`~/.harness/bin/ledger-note.sh`）へ1行残す

## 11. 失敗と中断

- マージ後に問題が見つかったら、そのバッチを打ち消す PR（revert）で戻し、読み戻しと実機確認をやり直す。強制 push はしない
- 実機が使えない（他のセッションが使用中、ミラーリングが切れている など）ときは、自動の確認で進める。実機の確認は「未確認」と記録し、次に実機を使うときに必ず済ませる
