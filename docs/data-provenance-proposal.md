# 出典（provenance）の恒久対策 — 提案 / 2026-08-17

## なぜこの文書があるか

Codex の第三者レビュー（指摘3）:

> 出典規律が文書の停止だけに依存している。`schemas/index.ts` と `types/core.ts` とも
> `source` は任意で、`githubMachineService.ts` は未指定のまま取り込む。
> **主防御はデータリポジトリ側の CI に置くべき。**

きっかけは slot-analyzer-ios の `docs/loop.md`（2026-08-16 に廃止）に
「**機種データを1つ以上アップロード**」「**未確定の確率は近似値でOK**」という
自動実行プロンプトが眠っていたこと。文書を止めても、手動追加や別経路は防げない。

**⚠️ 本文書は提案であり、実装していない。** スキーマ変更は iOS / Android / pachi-manager が
消費する契約の変更なので、ユーザーの判断を待つ。

---

## 現状（2026-08-17 実測）

| 項目 | 実測 |
|---|---|
| `source` を持つ機種 | **149 / 149（100%）** |
| うち **URL 形式** | **0台** |
| 実際の中身 | 「一撃、なな徹」のような**サイト名のみ** |
| スキーマ上の必須性 | **required ではない**（required は name / type / roles / author / version / lastUpdated の6つ） |

つまり **`source` 100% は「出典が確認できる」を意味しない**。
どのページを見たのか・いつ取得したのかが無いため、第三者が数値を追試できない。

### なぜ「required 化」だけでは効果がないか

既に 100% 埋まっているので、`required` を足しても**通過するデータの集合は変わらない**。
防げるのは「今後の入れ忘れ」だけで、**内容の検証可能性は1ミリも上がらない**。

---

## 案

### 案A: `source` を required にする

- 効果: **ほぼゼロ**（既に100%）。今後の入れ忘れのみ防ぐ
- コスト: ゼロ（既存149台は全て通る）
- 判定: **単独では意味がない**。案Cの一部として実施するなら可

### 案B: `source` を構造化して全機種に遡及適用する

```json
"source": {
  "refs": [
    { "url": "https://...", "title": "一撃 - マイジャグラーV", "retrievedAt": "2026-03-27" }
  ],
  "note": "小役確率はメーカー公式、設定差は実戦値"
}
```

- 効果: **完全**。全データが検証可能になる
- コスト: 🔴 **既存149台の書き直し**。しかも多くは 2026-03 に登録されており、
  **当時どのページを見たか遡れない可能性が高い**
- 判定: 理想だが**遡及適用は現実的でない**

### 案C: 段階導入（新規・更新分のみ構造化を要求） 🥇

- `source` を `string | object` の union にする（既存の string 形式は有効のまま）
- validator が「**新規追加、または `roles` / 確率値の変更を伴う更新**」のときだけ object 形式を要求
- 既存の string 形式は**警告のみ**（エラーにしない）
- 効果: **今後のデータは検証可能になる**。既存は現状維持
- コスト: 中（`schemas/machine.schema.json` の union 化 + validator に差分判定を追加）
- 判定: **現実的で、実害の方向を止められる**

### 案D: PR テンプレート + CI チェック（案Cの補助）

- 数値変更を伴う PR に「出典 URL」「取得日」の記載を必須化する
- 効果: 人間のレビューに依存するが、機械が拾えない文脈を補える
- コスト: 小
- 判定: 案Cと併用する

**推奨: 案C + 案D。** 案Aは案Cに含める。案Bは遡及適用しない。

## 影響範囲（消費側）

| 消費側 | 使っているフィールド | union 化の影響 |
|---|---|---|
| slot-analyzer-ios | `schemas/index.ts`（zod）で `source` は optional string | 🔴 **union 対応が必要**。string のみを期待しているため object が来ると弾く可能性 |
| pachi-manager | `index.json` の `id` / `name` / `type` / `tags` のみ | ✅ **影響なし**（機種 JSON 本体を取得しない） |
| slot-analyzer_android | 未実装（ドキュメント2ファイルのみ） | ✅ 影響なし |

⚠️ **iOS 側を先に union 対応してからデータ側を変える**こと。逆順だと、
新形式のデータを既存アプリが弾く。iOS は OTA も実質使っていない（配信実績ゼロ）ため、
**アプリ更新が行き渡るまでのラグを見込む必要がある**。

## 未検証の点（正直な記載）

- **既存149台の `source` から実際に出典を遡れるかは未確認。** 「一撃」「なな徹」は
  実在の解析サイトだが、当時のページが残っているか、数値が今も一致するかは調べていない
- **案Cの「数値変更を伴う更新」を validator がどう判定するかは未設計。**
  git diff を見るのか、前バージョンとの比較を持つのか。実装時に決める必要がある
- **そもそもこの対策が必要な頻度が分からない。** 出典不明データが実際に混入した記録は無い。
  loop.md が実行された形跡も確認していない（PDCA_LOG.md は Cycle 1-2 で止まっている）。
  **リスクは実在するが、発生実績はゼロ**という状態
