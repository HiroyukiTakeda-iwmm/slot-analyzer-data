# 出典（provenance）の恒久対策 — 提案 / 2026-08-17（rev2）

## なぜこの文書があるか

Codex の第三者レビュー指摘:

> 出典規律が文書の停止だけに依存している。`source` は任意で、消費側は未指定のまま取り込む。
> **主防御はデータリポジトリ側の CI に置くべき。**

きっかけは slot-analyzer-ios の `docs/loop.md`（2026-08-16 に廃止）に
「**機種データを1つ以上アップロード**」「**未確定の確率は近似値でOK**」という
自動実行プロンプトが眠っていたこと。文書を止めても、手動追加や別経路は防げない。

**⚠️ 本文書は提案であり、実装していない。**

> rev2（2026-08-17）: 初版の実測値に誤りがあり、Codex の再レビューで6件の指摘を受けた。
> 特に「URL 形式は0台」は**測定方法が雑だった**（`startswith('http')` で判定したため、
> 先頭以外に URL がある場合を取りこぼした）。実測を正し、推奨案も差し替えた。

## 案

### 案A: `source` を required にする

- 既存149件への効果は**ゼロ**（既に100%が非空）
- ただし**将来の欠落防止には効果がある**（スキーマが受理する入力集合は確実に狭まる）
- 検証可能性は改善しない。`required` だけでは空文字も通るので `minLength` も要る
- 判定: **安価な一次防御として価値はある**。ただし単独では目的を達しない

### 案B: `source` を構造化して全機種に遡及適用する

- 効果: 完全に近いが、**「URL があること」と「その数値を追試できること」は別**
- コスト: 🔴 既存149台の書き直し。多くは 2026-03 登録で**当時のページを遡れない可能性が高い**
- 判定: 遡及適用は非現実的

### 案C: `source` を `string | object` の union にし、新規・変更時のみ object を要求

- 判定: ⚠️ **rev2 で推奨から降格**。理由は下の案E を参照（union は消費側の互換を壊しうる）

### 案D: PR テンプレート + CI の差分ポリシーチェック（案Eの補助）

- 数値変更を伴う PR に出典 URL・取得日の記載を求める
- 判定: 併用する価値あり

### 案E: `source` を維持したまま加算的に `provenance` を足す 🥇 **推奨（rev2）**

```json
{
  "source": "一撃、なな徹",
  "provenance": {
    "refs": [
      { "url": "https://...", "title": "…", "retrievedAt": "2026-08-17",
        "covers": ["roles.ぶどう", "confirmationEvents"] }
    ]
  }
}
```

- **既存の `source` を1文字も変えない**ので、消費側が壊れない
- 新形式は**追加フィールド**なので、知らない消費者は無視する
  （iOS の zod は既定で未知キーを strip する。`.passthrough()` でない限り壊れない — **要確認**）
- `schemas/machine.schema.json` は `additionalProperties: false` なので**スキーマへの追加は必須**
- 判定: **union より安全で、段階導入と両立する**

## 「provenance を要求する変更」の定義（Codex 指摘2）

案C の初版は「`roles` / 確率値の変更」しか対象にしていなかった。しかし
`confirmationEvents`・終了画面の確定設定・示唆内容・ゾーンなど、**数値でない根拠依存データ**が
既存 string のまま通ってしまう。

→ 対象を**明示的なフィールド一覧（または JSON パス規則）**で定義する:

```
roles[].probabilities.*        確率値
confirmationEvents[].confirmedSettings / excludedSettings
endScreens / endScreenGroups の設定対応
zones[].* の確率
trialSuccessRates.*
specialSettings / modeTransitions
```

⚠️ **「URL が存在する」と「内容を追試・立証できる」は別**。`covers` で対象を紐づけても、
リンク切れ・改稿は防げない。**「完全に検証可能になる」とは書かない。**

## 差分判定は validator ではなく CI で行う（Codex 指摘3）

現行の `scripts/validate.mjs` は**現行ツリーしか読まない**ため、更新前との比較ができない。
`.github/workflows/validate.yml` も checkout 後に通常の validator を実行するだけで、
比較基準を渡していない。

→ **CI の差分ポリシーチェックとして設計する**:

- PR では base SHA、main への push では event の before SHA を取得
- 履歴を明示的に fetch（shallow clone だと base が無い）
- 新旧 JSON をパースして**意味的に**比較（キー順・整形の差でノイズを出さない）
- **base 取得不能時は fail closed**（素通りさせない）
- テスト対象に新規・rename・削除・複数 commit・直接 push を含める
